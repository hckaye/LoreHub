# ADR 0002: セルフホステッドランナーとセルフホステッド Lore Server

[English](0002-self-hosted-runners-and-lore-servers.md) | [日本語](0002-self-hosted-runners-and-lore-servers.ja.md)

- Status: Proposed
- Date: 2026-08-13

## Context

現在の LoreHub は、管理された 1 台の Lore Server と、運用者が起動する CI ワーカー群を前提にしている。

- `LOREHUB_LORE_PUBLIC_URL` と `LOREHUB_LORE_INTERNAL_URL` は `LOREHUB_LORE_ROOT_DOMAIN` 配下の単一の
  管理された `lores://` エンドポイントを指す必要があり、設定検証がそれ以外を拒否する。すべてのリポジトリは
  プロビジョニング時にこのグローバル値から `lore_url` を受け取り、SDK クライアントはリポジトリ URL の
  authority を常に単一の設定済みオリジンへ書き換える。例外はリポジトリインポート API で、形式検証の後、
  呼び出し側が送った `loreUrl` をそのまま保存する。
- CI は `lorehub runner` コマンドで動く。ワーカーはプロセス内の信頼済みコンポーネントで、PostgreSQL の
  ジョブキューを直接読み、Actions シークレットキーで実行コンテキストの秘密情報を復号し、Lore 署名鍵で
  ジョブトークンに署名し、API と同じファイル領域にログと成果物を書き込む。ランナーの識別も登録もない。
  実行単位は workflow 全体で、エンキューは workflow 実行ごとに 1 行の `ci_jobs` を作り、`runs-on` は単一の
  スカラーラベルしか受け付けず、ワーカーは workflow 全体を `act` に渡す。`ci_jobs.runner_labels` はスキーマ
  に存在するが、書き込みも読み取りもされていない。
- マシンクレデンシャルには 1 つのパターンがある。パーソナルアクセストークンは（`SecretCodec` による鍵付き）
  HMAC-SHA-256 ダイジェストで保存され、有効期限・最終使用・失効の列を持つ。
- Lore のポリシー / 監視フックは mTLS 背後の HTTPS/JSON エンドポイントである。検証は CA と共通のクライアント
  CN（`lore-policy-hook`）のみを確認し、個々の Lore Server を識別しない。
- リポジトリは Organization 所有である。現時点で個人リポジトリの名前空間はない。

この構成では、LoreHub 運用者が全テナント分の中央 Lore Server とランナー群を用意する必要がある。運用者が
求める既定は逆で、テナントが自前の計算資源とストレージを持ち込み、インストール側が運用する容量は有償提供に
したい。

## Decision

リポジトリストレージと CI 実行は既定で持ち込み（bring-your-own）とする。Organization は GitHub Actions と
同様の登録フローで自前の Lore Server とランナーを登録する。インストール側が運用する容量（管理された
Lore Server と管理されたランナー群）は、インスタンス管理者が明示的に付与するエンタイトルメントの背後に
置く。アップグレード前から存在する Organization は grandfather し、その場では何も壊れないようにする。

### インスタンス管理者とエンタイトルメント

- インスタンス管理者は設定からブートストラップする。`LOREHUB_INSTANCE_ADMIN_USERNAMES` が管理 API を呼べる
  ユーザーを指名する。付与と取り消しは監査ログに記録する。
- 新テーブル `entitlements`: `organization_id` と `user_id` を別々の nullable 外部キー列とし、ちょうど一方
  だけが設定される CHECK、`feature`（CHECK: `hosted_lore_server` / `hosted_runners`）、`granted_by`
  （nullable）、`grant_source`（CHECK: `admin` / `migration`）、`created_at`、`revoked_at`
  （CHECK `revoked_at >= created_at`）、対象と feature ごとの有効行に対する部分ユニークインデックスを持つ。
- このテーブルを導入するマイグレーションは、アップグレード時点で存在するすべての Organization に
  `grant_source = 'migration'` で両エンタイトルメントを backfill する。既存インストールはそのまま動き続け、
  アップグレード後に作られた Organization だけがエンタイトルメントなしで始まる。
- エンタイトルメント確認は admission snapshot 方式とする。確認は作業の受け入れ時（リポジトリ作成、実行の
  エンキュー）に行う。失効は以後の受け入れにだけ影響し、待機中・実行中の作業は完了できる。失効時の即時
  キャンセルは初回イテレーションの範囲外と明記する。
- 課金や支払いの処理は範囲外で、プラットフォームが確認する事実はエンタイトルメント行だけとする。

### セルフホステッドランナー

ランナーの識別と登録:

- 新テーブル `ci_runners`: id、別々のスコープ列（`repository_id`、`organization_id`）と
  `actions_execution_context_entries` と同じ複合外部キーパターン（リポジトリスコープのランナーが
  Organization 境界を越えられない）、name、labels（jsonb、小文字に正規化し、件数・長さ・型を制約）、
  クレデンシャルダイジェスト、クレデンシャルの有効期限と最終使用、`revoked_at`、ランナーのバージョン、
  `last_seen_at`。表示ステータス（`offline` / `idle` / `busy`）はハートビートと有効なリースから導出し、
  自己申告値は使わない。
- 新テーブル `runner_registration_tokens`: スコープ列、トークンダイジェスト、`expires_at`、`consumed_at`、
  `created_by`。設定ページ（リポジトリまたは Organization）がプレフィックス `lhrr_` の短命な登録トークンを
  発行する。交換は `UPDATE ... WHERE consumed_at IS NULL AND expires_at > now()` の原子的な消費とする。
- `lorehub-runner configure --url <lorehub>` は登録トークンを標準入力から読み（`--token` フラグも用意する
  が、プロセス一覧に漏れる旨を警告する）、プレフィックス `lhr_` の長命なランナークレデンシャルに交換して
  ローカル設定を保存する。クレデンシャルダイジェストは専用の HMAC キー（`LOREHUB_RUNNER_TOKEN_KEY`）と
  ローテーション用の key-id 列を使い、API トークン鍵の変更で全エージェントが止まらないようにする。
  `lorehub-runner run` がデーモンを起動し、インストールスクリプトが GitHub ランナーの `svc.sh` に相当する
  systemd ユニットを提供する。

ランナー用 control-plane API（新規）:

- 外部ランナーは PostgreSQL、Actions シークレットキー、Lore 署名鍵に一切触れない。これらは API プロセス内に
  留める。デーモンはランナークレデンシャルで認証される HTTPS プロトコルを話す: claim、ハートビート、
  キャンセル確認、実行コンテキスト取得、ジョブトークン発行、ログアップロード、成果物アップロード、完了報告。
- claim は 1 トランザクションで、クレデンシャルをランナー行に解決し、有効かつ未失効であること、ジョブの
  リポジトリがランナーのスコープ内にあること、ジョブのラベルがランナーのラベルの部分集合であること、ジョブの
  `execution_target` が `self_hosted` であることを検証し、リースにランナー id を書き込む。ハートビート、
  コンテキスト取得、トークン発行、アップロード、完了報告はすべて、提示されたクレデンシャルがリース保持
  ランナーのものであることを検証する。アップロードはジョブ・attempt・リースに束縛し、サイズ上限と再送時の
  冪等性を定義する。
- 管理されたランナー群は引き続きプロセス内ワーカー経路を使い、`execution_target = 'managed'` のジョブだけを
  取得する。

ルーティング:

- エンキューは workflow の正規化済み `runs-on` ラベルを `ci_jobs.runner_labels` に保存し、
  `execution_target` を設定する: ラベルに `self-hosted` を含む場合は `self_hosted`、`ubuntu-latest` などの
  プラットフォームラベルは `managed`。ラベルが一致してもセルフホステッドランナーが managed ジョブを claim
  することはできず、逆も同様とする。
- 実行単位が workflow 全体であるため、初回イテレーションでは 1 つの workflow 内の全ジョブが同じ正規化済み
  `runs-on` を使うことを要求し、混在した指定は workflow 検証が実行可能なエラーで拒否する。ジョブ単位の
  ルーティングにはスケジューラ再設計（ジョブ依存、outputs、artifacts）が必要なため先送りする。
- `hosted_runners` エンタイトルメントなしで managed ラベルに解決される実行は、エンキューのエラーではなく、
  機械可読な `failure_reason`（新列）を持つ完了済み・失敗の実行として記録する。エンキューからエラーを返す
  と、同一トランザクション内の workflow カタログとブランチ監視までロールバックされ、poller が同じ
  リビジョンを繰り返してしまう。

実行環境:

- 初回イテレーションは現在のワーカーに合わせて Linux/amd64 のコンテナランナーを対象とする。インストール
  パッケージは Docker エンジンの mTLS エンドポイント、egress プロキシ、`docs/runner-actions.md` の信頼境界
  ガイダンスが求めるランタイム分離を構成する。自前ハードウェア上の分離はテナントが所有する。
- 設定 UI は、Organization スコープのランナーがスコープ内の全リポジトリのソース・シークレット・ジョブ
  トークンを受け取ることを警告する。

### セルフホステッド Lore Server

登録と識別:

- 新テーブル `lore_servers`: id、スコープ（`instance` / `organization`、CHECK 付きの別々の列）、name、公開
  `lores://` URL、status、クレデンシャルダイジェスト、Lore ビルドバージョン、`last_seen_at`、ヘルス
  メタデータ。インスタンスのサーバーは起動時に設定から作られる 1 行の `instance` スコープ行として表現する。
- ランナー登録と同じ形式と原子的消費を持つ新テーブル `lore_server_registration_tokens`。Organization 設定が
  プレフィックス `lhsr_` のトークンを発行し、Lore Server ホスト上の `lorehub-lores-agent configure` が
  （ランナーと同じく標準入力優先で）プレフィックス `lhss_` のサーバークレデンシャルに交換し、公開する
  `lores://` URL を記録する。`lorehub-lores-agent run` がデーモンを起動し、通常の HTTP API でヘルス・ビルド
  バージョン・フックモジュールの状態を LoreHub に報告する。
- ポリシー統合は `docs/operations/control-plane-authorization.md` に記載のとおりパッチ済み Lore ビルドを
  前提とするため、登録時に Lore ビルドとフックモジュールのバージョンをサポート範囲と照合する。
- ユーザースコープのサーバーとランナーはスキーマ形状（nullable な `user_id` スコープ列）として定義するが、
  個人リポジトリの名前空間が存在するまで休眠させる。初回イテレーションは `instance` と `organization` の
  スコープだけを出荷する。

サーバー個体の信頼:

- 共有の `lore-policy-hook` クライアント証明書はサーバーを区別できないため、テナントには配布しない。
  LoreHub は `lore_server_id` を識別子に持つサーバー個体別の mTLS クライアント証明書を発行し、エージェント
  経由で配布・更新し、サーバー削除時に失効させる。ポリシー / 監視エンドポイントは証明書の識別子をサーバー
  行に解決し、リクエスト中のリポジトリがそのサーバーに割り当てられていることを検証する。これにより、侵害
  されたテナントサーバーは自分のリポジトリの分しか発言できない。
- 認証は集中管理のままとする。登録されたサーバーは認証とポリシーを LoreHub の Lore Auth / ポリシー
  エンドポイントへ委譲し続け、これらは管理されたルートドメイン配下に留まる。設定のルートドメイン制約を
  緩めるのはデータプレーンのリポジトリ URL だけである。

サーバー選択とデータプレーン:

- リポジトリに既存の `lore_url` と並ぶ `lore_server_id` 外部キーを追加する。作成時の選択は、リポジトリ単位
  の明示的な選択、次に Organization の既定（登録済みサーバーを 1 つ指名する設定）、最後にインスタンスの
  サーバー。インスタンスのサーバーを使うには `hosted_lore_server` エンタイトルメントが必要で、ない場合は
  プロビジョニングのトランザクション内で、サーバー登録を案内するエラーとともに作成を失敗させる。
- 割り当ては、すでに Organization 行をロックしている `BeginRepositoryProvisioning` と同じトランザクション
  内で行う。マイグレーションは既存の全リポジトリの `lore_server_id` をインスタンスのサーバー行に backfill
  する。
- リポジトリインポート API は `loreServerId` を必須とし、インポートする URL の authority が登録済みサーバー
  の URL と一致することを検証する。自由入力のインポート URL は廃止する。
- SDK クライアントは単一の書き換えオリジンをやめ、`lore_server_id` から公開 / トランスポートの authority を
  返すリゾルバーに置き換え、クレデンシャルキャッシュをサーバー id と正規化済みトランスポート authority で
  キーづけする。

到達性とヘルス:

| 通信                              | 方向                     | 目的                                             |
| --------------------------------- | ------------------------ | ------------------------------------------------ |
| LoreHub API から Lore Server      | LoreHub から外向き       | プロビジョニング、ブランチ読み取り、マージ、削除 |
| Lore クライアントから Lore Server | 利用者マシンから         | クローン、同期、プッシュ                         |
| Lore Server から LoreHub          | サーバーから外向き       | Lore Auth、JWKS、ポリシー、監視                  |
| エージェントから LoreHub          | サーバーホストから外向き | 登録、ハートビート、ヘルス                       |

- エージェントのハートビートはホストの生存を示すだけで、データプレーンの到達性は示さない。サーバーの
  ヘルスはハートビートと API ホストからの能動的な TLS プローブを組み合わせ、エンドポイントに到達できない
  場合、プロビジョニングはヘルスエラーで即座に失敗する。`last_seen_at` 単独を到達性の証拠として扱わない。
- LoreHub が接続する URL はテナントが指定するため、リゾルバーは運用者が明示的に許可
  （`LOREHUB_LORE_ALLOW_PRIVATE_SERVERS`）しない限りプライベート / 予約アドレスを拒否し、接続タイムアウトを
  適用する。
- 既存リポジトリのサーバー間移動は範囲外とする。移行ツールは将来の ADR で扱う。

### 強制の一覧

| 操作                               | エンタイトルメントなし                | エンタイトルメントあり                 |
| ---------------------------------- | ------------------------------------- | -------------------------------------- |
| リポジトリ作成（サーバー未登録）   | プロビジョニング内で案内付き拒否      | インスタンスのサーバーに配置           |
| リポジトリ作成（既定サーバーあり） | そのサーバーにプロビジョニング        | 同左、インスタンスのサーバーも選択可能 |
| リポジトリインポート               | 登録済みサーバー id が必須            | 同左、インスタンスのサーバーも許可     |
| `runs-on: self-hosted` の実行      | 登録済みランナーへルーティング        | 同左                                   |
| `runs-on: ubuntu-latest` の実行    | `failure_reason` 付きの失敗として記録 | 管理されたランナー群へルーティング     |

grandfather された Organization はマイグレーション付与で両エンタイトルメントを持つため、アップグレード
時点で挙動は変わらない。

## Rejected alternatives

### 共有 Lore Server を 1 台のまま内部でシャーディングする

パーティション単位のシャーディングではストレージ費用がすべて運用者に残り、データ所在や規模の要件を持つ
テナントの助けにならない。単一ルートドメイン前提も設定に残り続ける。

### リポジトリごとの自由入力サーバー URL

登録なしで任意の `lores://` URL をリポジトリ設定やインポート API に受け付けると、ヘルス報告もクレデンシャル
信頼もサーバー個体のポリシー識別もサーバー失効の手段もなくなる。既存のインポート挙動も同じ理由で登録済み
サーバーに限定する。

### プロセス内ワーカーをそのままセルフホステッドランナーとして配る

現在のワーカーバイナリをテナントに配ると、データベースのクレデンシャル、シークレット暗号鍵、トークン署名鍵
を渡すことになる。外部実行には、リースに限定された狭い control-plane API が必須であり、これは最適化では
なく本 ADR の一部である。

### テナントネットワークへの運用者管理トンネル

LoreHub がテナントネットワークへ到達するために運用者管理のトンネルを要求すると、エージェントモデルなら
不要なインフラが増える。エージェントはアウトバウンドで登録し、サーバー自体は公開した `lores://`
エンドポイントでクライアントと LoreHub から到達可能であればよい。これは Lore クライアントの既存の接続方法
と一致する。

## Operational consequences

- 登録された Lore Server は、公開した `lores://` エンドポイントを Lore クライアントと LoreHub API ホストに
  公開し、LoreHub の認証・ポリシー・API エンドポイントへアウトバウンドで到達できる必要がある。
- セルフホステッドランナーのホストは ADR 0001 と `docs/runner-actions.md` の信頼境界の指針に従う。テナント
  ごとに 1 つの信頼ドメインとし、コンテナ分離はインストールパッケージが構成し、自前ハードウェア上の分離は
  テナントが所有する。
- `runner` compose プロファイルと管理された Lore Server は、開発用と、自身にエンタイトルメントを付与する
  インストール向けに引き続き利用できる。
- 文書化する新しい対象: ランナー登録、サーバー登録、エンタイトルメント管理、ランナー用 control-plane API、
  サーバー個体別証明書のライフサイクル。
