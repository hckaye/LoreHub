# ADR 0002: セルフホステッドランナーとセルフホステッド Lore Server

[English](0002-self-hosted-runners-and-lore-servers.md) | [日本語](0002-self-hosted-runners-and-lore-servers.ja.md)

- Status: Proposed
- Date: 2026-08-13

## Context

現在の LoreHub は、管理された 1 台の Lore Server と、運用者が起動する CI ワーカー群を前提にしている。

- `LOREHUB_LORE_PUBLIC_URL` と `LOREHUB_LORE_INTERNAL_URL` は `LOREHUB_LORE_ROOT_DOMAIN` 配下の単一の
  管理された `lores://` エンドポイントを指す必要があり、設定検証がそれ以外を拒否する。すべてのリポジトリは
  プロビジョニング時にこのグローバル値から `lore_url` を受け取り、SDK クライアントはリポジトリ URL の
  authority を常に単一の設定済みオリジンへ書き換える。
- CI は `lorehub runner` コマンドで動く。ワーカーは運用者が起動する信頼済みプロセスで、`FOR UPDATE SKIP
LOCKED` とリースにより待機中のジョブを無条件に取得する。ランナーの識別も登録もラベルルーティングもなく、
  `ci_jobs.runner_labels` は書き込まれるだけで読まれない。

この構成では、LoreHub 運用者が全テナント分の中央 Lore Server とランナー群を用意する必要があり、どちらも
費用が大きい。運用者が求める既定は逆で、テナントが自前の計算資源とストレージを持ち込み、インストール側が
運用する容量は有償提供にしたい。

## Decision

リポジトリストレージと CI 実行は既定で持ち込み（bring-your-own）とする。Organization とユーザーは
GitHub Actions と同様の登録フローで自前の Lore Server とランナーを登録する。インストール側が運用する容量
（管理された Lore Server と管理されたランナー群）は、インスタンス管理者が明示的に付与するエンタイトルメント
の背後に置く。

### エンタイトルメント

- 新テーブル `entitlements`: subject（`organization` または `user` と対応する id）、`feature`、
  `granted_by`、`created_at`、`revoked_at`。feature は `hosted_lore_server` と `hosted_runners` から始める。
- インスタンス管理者が管理 API でエンタイトルメントを付与・取り消しする。課金や支払いの処理はこの ADR の
  範囲外で、プラットフォームが確認する事実はエンタイトルメント行だけとする。
- 既定では何も付与しない。新しい Organization やユーザーはセルフホステッド容量だけを使える。

### セルフホステッドランナー

- 新テーブル `ci_runners`: id、scope（`repository` / `organization` / `user`）、所有者参照、name、labels
  (jsonb)、status（`offline` / `idle` / `busy`）、クレデンシャルダイジェスト、`last_seen_at`、ランナーの
  バージョン。複合外部キーは `actions_execution_context_entries` と同じ形式に従い、リポジトリスコープの
  ランナーが Organization 境界を越えられないようにする。
- 登録は GitHub Actions ランナーのフローに合わせる。設定ページ（リポジトリ / Organization / ユーザー）が
  プレフィックス `lhrr_` の短命な登録トークンを発行する。ランナーホストで `lorehub-runner configure --url
<lorehub> --token <lhrr_...>` を実行すると、登録トークンをプレフィックス `lhr_` の長命なランナー
  クレデンシャルに交換し、パーソナルアクセストークンと同じく SHA-256 ダイジェストで保存する。
  `lorehub-runner run` がデーモンを起動し、インストールスクリプトが GitHub ランナーの `svc.sh` に相当する
  systemd ユニットを提供する。
- デーモンは既存のワーカー実行経路（チェックアウト、`act`、mTLS 経由の Docker、ログアップロード、ジョブ
  トークン）を再利用する。ジョブ取得クエリに 2 つのフィルタを追加する: ジョブのリポジトリがランナーの
  スコープ内にあること、ジョブの `runner_labels` がランナーのラベルの部分集合であること。ジョブトークンは
  引き続き単一のジョブリースに限定する。
- `runs-on` のルーティング: `self-hosted` ラベル（単独またはカスタムラベル併用）は登録済みランナーへ
  ルーティングする。`ubuntu-latest` などのプラットフォームラベルは管理されたランナー群へルーティングし、
  リポジトリ所有者に `hosted_runners` エンタイトルメントを要求する。エンタイトルメントなしで管理ラベルに
  解決される実行は、永久に待たせる代わりにエンキュー時点で説明付きアノテーションとともに失敗させる。
- 管理されたランナー群は既存の `lorehub runner` コマンドで動き続け、エンタイトルメント確認を通過して
  プラットフォームラベルを持つジョブだけを取得するようになる。

### セルフホステッド Lore Server

- 新テーブル `lore_servers`: id、scope（`instance` / `organization` / `user`）、所有者参照、name、公開
  `lores://` URL、status、クレデンシャルダイジェスト、`last_seen_at`、ヘルスメタデータ。インスタンスの
  サーバーは起動時に設定から作られる 1 行の `instance` スコープ行として表現する。
- 登録はランナーと同じ形にする。Organization またはユーザーの設定がプレフィックス `lhsr_` の登録トークン
  を発行する。Lore Server を動かすホスト上で `lorehub-lores-agent configure` がトークンをサーバー
  クレデンシャルに交換し、公開する `lores://` URL を記録する。`lorehub-lores-agent run` がデーモンを起動
  し、通常の HTTP API で LoreHub にヘルスとバージョンを報告する。
- 認証は集中管理のままとする。登録されたサーバーは認証とポリシーを LoreHub の既存の Lore Auth / ポリシー
  gRPC エンドポイントへ委譲し続け、エージェントがその設定をサーバーに行う。リポジトリデータの置き場所に
  かかわらず、LoreHub が単一の認証権威であり続ける。
- リポジトリ作成時のサーバー選択: リポジトリ単位の明示的な選択が最優先、次に所有者の既定（登録済み
  サーバーを 1 つ指名する Organization / ユーザー単位の設定）、最後にインスタンスのサーバー。インスタンス
  のサーバーを使うには `hosted_lore_server` エンタイトルメントが必要で、ない場合はサーバー登録を案内する
  エラーで作成を失敗させる。
- 解決されたサーバーは今までどおり `repositories.lore_url` に書き込むため、データプレーンは保存済み URL
  から動き続ける。SDK クライアントはすべての URL を単一のグローバルオリジンへ書き換えるのをやめ、サーバー
  行ごとにトランスポート authority を解決する。クレデンシャルキャッシュはすでにエンドポイント単位で
  キーづけされている。設定検証のルートドメイン制約はインスタンスのサーバーにだけ適用する。
- 既存リポジトリのサーバー間移動は範囲外とする。移行ツールは将来の ADR で扱う。

### 強制の一覧

| 操作                                       | エンタイトルメントなし         | エンタイトルメントあり                   |
| ------------------------------------------ | ------------------------------ | ---------------------------------------- |
| リポジトリ作成（サーバー未登録）           | 案内付きで拒否                 | インスタンスのサーバーにプロビジョニング |
| リポジトリ作成（所有者の既定サーバーあり） | そのサーバーにプロビジョニング | 同左、インスタンスのサーバーも選択可能   |
| `runs-on: self-hosted` の実行              | 登録済みランナーへルーティング | 同左                                     |
| `runs-on: ubuntu-latest` の実行            | エンキュー時に失敗             | 管理されたランナー群へルーティング       |

## Rejected alternatives

### 共有 Lore Server を 1 台のまま内部でシャーディングする

パーティション単位のシャーディングではストレージ費用がすべて運用者に残り、データ所在や規模の要件を持つ
テナントの助けにならない。単一ルートドメイン前提も設定に残り続ける。

### リポジトリごとの自由入力サーバー URL

登録なしで任意の `lores://` URL をリポジトリ設定に受け付けると、ヘルス報告もクレデンシャル信頼もサーバー
失効の手段もなくなる。タイプミスは作成時点でリポジトリを孤立させる。

### テナントネットワークへの運用者管理トンネル

LoreHub がテナントネットワークへ到達するために運用者管理のトンネルを要求すると、エージェントモデルなら
不要なインフラが増える。エージェントはアウトバウンドで登録し、サーバー自体は公開した `lores://`
エンドポイントでクライアントと LoreHub（プロビジョニング用）から到達可能であればよい。これは Lore
クライアントの既存の接続方法と一致する。

## Operational consequences

- 登録された Lore Server は、公開した `lores://` エンドポイントを Lore クライアントと LoreHub API ホスト
  の両方に公開する必要がある。エンドポイントに到達できない場合、プロビジョニングはヘルスエラーで即座に
  失敗する。
- セルフホステッドランナーのホストは ADR 0001 の信頼境界の指針に従う。テナントごとに 1 つの信頼ドメインと
  し、自前ハードウェア上の分離はテナントが所有する。
- `runner` compose プロファイルと管理された Lore Server は、開発用と、自身にエンタイトルメントを付与する
  インストール向けに引き続き利用できる。
- 文書化する新しい対象: ランナー登録、サーバー登録、エンタイトルメント管理。
